# ER 002: 2D bridge builder

## 2026-11-17

- **[action]** Milestone 2 started. Plan 002 written from the roadmap checks: 2.1 WebAssembly build and loader, 2.2 host world and bridge scene, 2.3 editor page, 2.4 record and replay. Milestone 1's record (ER 001) is closed at phase 1.7.
- **[assumption]** The bridge builder is a test bed, not a shippable mini-game (the open question from the spec, due at the start of this milestone). The owner said "proceed" to a recommendation of test bed, so work follows it; nothing here blocks switching later.
- **[decision]** Planning and building this milestone are both Sonnet's, as the roadmap table says. No Opus step is nominated.

## 2026-11-17 (phase 2.1)

- **[action]** Phase 2.1 done. `core/src/ffi.rs` is the boundary as a C-style interface (`rc_*` functions: host new and free, add node and beam, add force, step, state hash, node and beam counts, positions, events, render buffer, and the benchmark scene). `src/core.ts` loads the module from its bytes (Node and browser alike) and wraps the exports as typed methods; `test/wasm.test.ts` (7 tests, 1 opt-in) and `core/tests/ffi.rs` (5 tests) exercise the same functions natively and in WebAssembly. `pnpm test` now builds the wasm first (`pnpm build:wasm`, a release build for `wasm32-unknown-unknown`); `RIBCAGE_SLOW=1 pnpm test` adds the reported scene. `cargo test`, `pnpm test` and `pnpm typecheck` pass. `Vec3` is now `repr(C)`, so positions can be read in place.
- **[decision]** Raw C-style exports, no `wasm-bindgen` or `wasm-pack`. The module has no imports (a test checks it), is 63 KB, and has no generated glue to keep deterministic; the host reads output arrays straight out of linear memory. The cost is one hand-kept signature list (`ABI_VERSION`, checked at load) instead of generated bindings, fine for a boundary this small. Revisit only if the boundary grows past what a list can hold.
- **[decision]** A `Host` owns one world and is passed as a pointer: no global state (determinism list), several worlds possible. Positions out are `f32` triples written by `rc_write_render` once per rendered frame (layout rule 8), plus the full-precision array for tests and the recorder. The floating origin is the world origin until a scene needs one. **[assumption]**
- **[decision]** Hashes and counts cross the boundary as 64-bit integers, which JavaScript receives as signed `BigInt`; the loader converts with `BigInt.asUintN(64, ...)` so hashes print the same as the native `{:016x}`. (First test run failed on exactly this.)
- **[finding]** **Native and WebAssembly agree bit for bit.** The small benchmark scene after 120 steps (`0x935259e4d2c6ff87`), a hand-built hanging beam after 30 steps (`0xb62c7e7dd415f3a1`) and the reported 11,136-beam scene after 720 steps (`0x871092299f3cea56`, the end hash from ER 001, phase 1.7) give identical hashes natively and in Node's WebAssembly. That covers the own sin/cos (the scene is built with them), the solver, damping, and the yield and break code; the first check that milestone 1's determinism list holds across the two builds. The same goldens are written in both test files.
- **[finding]** **First WebAssembly timing**, reported scene, 17 substeps, 600 steps after 120 warm-up, one run in Node v22 on the same noisy machine: mean 8.8 ms, median 7.4 ms, p95 12.8 ms per step. The native release build, run just before: mean 6.4 ms (33 ns per beam solve). So WebAssembly in Node costs roughly 1.2 to 1.4 times native here. One run each; read it as "close to native", not as a figure. A browser's engine is not measured yet (2.3).
- **[finding]** `pnpm typecheck` rejects a Node `Buffer` as `BufferSource` (its buffer may be shared); the test copies the file into a plain `Uint8Array`. Browser code passes an `ArrayBuffer` from `fetch` and is not affected.
- **[question]** The roadmap check "the core runs in the browser as WebAssembly" is not ticked yet: it is proven in Node, and a browser needs the TypeScript compiled and served. Phase 2.3 chooses how (plain `tsc` emit with no bundler is the leading option: no new dependency). Not blocking 2.2.

## 2026-11-17 (phase 2.2)

- **[action]** Phase 2.2 done. The command buffer (layout rule 8) is in: `core/src/command.rs` (a 64-byte record with a kind, up to two indices and six numbers; kinds add node, add beam, delete node, delete beam, add force, set inverse mass), applied in list order before a step through `rc_commands_reserve` and `rc_apply_commands`, with one result slot per record. `src/commands.ts` fills a batch; `src/world.ts` wraps one host (apply, step, events, snapshot); `src/bridge.ts` builds the truss and the rolling load as command lists. Beam output for drawing is new: `rc_write_beams` gives beam ends and a signed strain ratio, and flags come straight from the core. `ABI_VERSION` is 2; the loader also checks the record size. `cargo test`, `pnpm test` and `pnpm typecheck` pass (`core/tests/commands.rs` 5 tests, `test/bridge.test.ts` 7).
- **[decision]** A record that makes no sense (a dead or missing node, a non-finite or negative number, an unknown kind, a zeroed record) is **rejected, not trapped**: its result slot reads `u32::MAX`, the rest of the batch still applies, and the same list rejects the same records on every run. The host can therefore fill the buffer from a saved recording or from the editor without a panic ever crossing the boundary. This replaces the "bad argument traps" line in `ffi.rs` for the command path; the old direct `rc_add_*` calls still trap and stay for tests.
- **[decision]** Forces are commands too (`CMD_ADD_FORCE`), so the truck's weight is in the saved lists and a replay needs nothing else (the check for 2.4, already exercised once in the test). `World::set_inv_mass` was added for pin and release; the editor needs it for supports.
- **[decision]** The strain ratio the core reports is the beam's total strain `(length - rest0) / rest0` divided by its yield strain (break strain if it has none), signed. One number per beam is what the colour scale in 2.3 needs: 0 is relaxed, 1 is at yield, negative is compression. A dead or broken beam reads 0.
- **[decision]** Host-built geometry uses `Math.sqrt`, never `Math.hypot`, for rest lengths: sqrt is exactly rounded in every engine, `hypot` is not, and the rest lengths are command data that a recording must reproduce. **[assumption]** `Math.sqrt` of a sum of two squares is enough for a planar truss.
- **[decision]** Bridge numbers (**[assumption]**, a test bed): eight 3 m bays, 3 m deep Warren truss with the deck on the bottom chord, 100 kg per node, damping 5000 N·s/m, yield strain 0.00125, break strain 0.01, steel-stiff `EA` of 2e8 N (strong) or 2e7 N (weak), a 3000 kg point load rolling at 4 m/s that is split between the two deck nodes beside it. Stiffer beams need more substeps (the rule's cap is 32); at 2e8 N the strong bridge uses 20, so it has room, and a steel beam of real size would be stiffer than the cap allows. A real steel member is stiffer still, so full-size steel needs a lower substep target (the open `c` question) or more mass per node; not a 2.2 problem.
- **[finding]** **Strong bridge holds.** Over the crossing (about 6 s) and 4 s after: no yield or break events, the largest strain is 47% of yield (sampled every 30 steps; the test checks every step and allows 60%), the lowest node is 1.6 cm below its start, and the deck is back within 5 mm of rest after the truck leaves. 20 substeps at most.
- **[finding]** **Under-built bridge breaks.** At a tenth of the stiffness and strength the first yields come within 0.1 s, when the truck is still on the first bay, and the first break follows within about 0.6 s; it then falls apart and is still falling at the end of the run (nothing catches it). Peak strain reaches about 5.6 times yield (a coarse sample). Yield always comes before the first break (a test).
- **[finding]** **z stays exactly 0** for both bridges over the whole run (a test checks every node), as the plan expected for in-plane forces.
- **[finding]** **Replay from the saved lists gives the same hash**: a fresh world fed only the byte lists (the build, then one list per step) ends at the same state hash and step count as the live run. This is most of what phase 2.4 needs; 2.4 adds the file format and the browser.
- **[finding]** **Memory growth is safe through the command path**: a batch of 60,000 `add node` records grows linear memory, and the results, positions and render buffer read back correctly afterwards (the loader makes its view after the call that grows memory).
- **[question]** The roadmap line "a load rolls across the bridge and an under-built bridge breaks" is ticked on the headless test. Its words are "you can see" in spirit; 2.3 shows it in the editor. Not blocking.
