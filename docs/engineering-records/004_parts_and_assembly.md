### The ordering issue (rigid engine and pod)

- **[decision]** **Rigid bodies stay in milestone 5; the roadmap order is kept.** The brief recommended moving a minimal rigid body (riding nodes, no sleeping) to the start of milestone 4, because a heavy engine on a light truss is the mass-ratio problem. In this milestone the engine and pod are compact, fully braced lattices with their mass spread over their nodes, every node flagged never-live in the part data. Why: (1) the problem the brief names does not arise for the parts of this milestone: the hopper's engine nodes (about 44 kg) and tank nodes (about 50 kg) are nearly equal, and the generators enforce a node-mass ratio of at most 10 across a craft; (2) the riding endpoint changes the one correction kernel that beams and contacts share, and it is best designed once, with sleeping, merging and splitting, in milestone 5's Opus session, rather than twice; (3) the never-live flag, segments, seams and section properties are emitted now, so milestone 5 needs no change to any generator; (4) keeping the order needs no roadmap change. Cost: the engine and pod flex very slightly where a rigid body would not; 4.11 measures it. Plan 001's open question on this is answered "no". **Confirmed by the owner** after the plan was written; Plan 001's open question is ticked with that answer.

### Parts and assembly

- **[decision]** **Generators in TypeScript, emitting commands.** Same pattern as `src/design.ts` and `src/scenes3d.ts`: the core stays a solver of nodes and beams and never learns what a tank is. Parts and the assembler are pure functions, so Node tests cover them without the core.
- **[decision]** **No sine or cosine in generators.** Ring node counts are limited to 4, 6, 8, 12, 16 and 24, whose angles are multiples of 15° or 22.5°; their cosines and sines are built from `sqrt(2)`, `sqrt(3)` and the half-angle formula `cos(θ/2) = sqrt((1 + cos θ) / 2)`, all exactly rounded operations. Every JavaScript engine therefore gives the same bits, and the root yaw and the clock use the same table. **[assumption]** Six counts are enough for test-bed parts; others wait for a reason.
- **[decision]** **Part mass is a parameter; members set a floor.** Each member's own mass (density × area × length) goes half to each end node; the rest of the stated mass ("contents": propellant, equipment, crew) is spread evenly over the part's nodes. A stated mass below the members' own mass is refused. This keeps real densities meaningful without making a tank's mass depend on its wall alone.
- **[decision]** **Segments.** One segment per bay for tanks and trusses, one per leg, one each for engine and pod (never-live) **[assumption]**. A merged node keeps the parent's segment; the child's beams that touch it are seam beams. Each seam carries its section properties: axial area `Σ A` of the members crossing the cut, and bending stiffness `Σ A · d²` with `d` each member's distance from the cut's centroid. Emitted and tested in 4.2 and 4.4, used from milestone 5.
- **[decision]** **Welding merges nodes; ring beams come from the parent.** Two coincident nodes joined by a zero-length beam would be the stiffest beam in the craft and set the substep count; merging avoids that and keeps the node count down. Duplicate ring beams (both parts' perimeter and chords on the same merged nodes) would double the ring's stiffness, so the child's are dropped. Tolerance 1 mm on ring radius, refused above. The weld is done at build time, at rest (spec stability guard "weld only at rest").
- **[decision]** **The clock is a permutation.** Turning a child about the ring axis by `k` ring steps is a renumbering of its ring nodes plus the exact rotation from the table above; no angle is ever stored, so a saved craft rebuilds to the same bits.
- **[decision]** **Craft file in JSON with one canonical order** (format, version, name, parts in id order of insertion, joins in insertion order, root), keys in a fixed order, numbers by JavaScript's shortest round-trip conversion (specified exactly by ECMAScript, so the same on every engine). Strict reading: unknown fields are refused rather than ignored, so load-then-save can never silently drop something. Version 1. **[assumption]** The damage layer (spec: broken beams and bent rest lengths) waits for the open question on whether wrecks persist.

### Thrust

- **[decision]** **Thrusters are a core feature, not host forces.** The host could send `CMD_ADD_FORCE` every step, but it only reads 32-bit render positions, so the direction would differ from the core's own 64-bit one; a recording would carry one force command per thruster node per step; and milestone 5's wake triggers ("a thrust change on it") need the core to know what thrust is. With two command kinds a recording carries only throttle changes.
- **[decision]** **Thrust acts along tail-to-head, half on each node, constant through the step.** Direction from positions at the start of the step, applied through `add_force` (layout rule 7), so it costs one square root per thruster per step and nothing per substep. The engine generator puts the head and tail on the engine's axis and braces both to both rings, so the thrust spreads into the lattice. A thruster keeps pushing if its engine breaks off (that is physical); it stops only if a node is deleted or the two coincide.
- **[decision]** **Throttle is rejected outside 0 to 1, not clamped**, like every other bad record (deterministic rejection, nothing silently changed). No gimbal and no fuel flow in this milestone; the hopper's mass is constant.
- **[decision]** **ABI 4**, decoder accepts 2, 3 and 4: ABI 4 only adds command kinds, so older lists mean the same; the two committed goldens are the guard that nothing else moved.

### Numerics (decided here against performant, semi-realistic, deterministic)

- **[decision]** **Real materials, stiffness scaled by `s = 0.1` [assumption].** Real steel members at real sizes are far past the 32-substep cap (ER 002, phase 2.2). Scaling only the modulus, and deriving the strains from the real stresses, keeps the forces at which members yield and break real: `yield strain = σ_y / (s·E)`, so the yield force is `s·E·A · σ_y / (s·E) = σ_y · A`. The cost is that structures stretch ten times further under load and ring about three times slower (`sqrt(10)`), which reads as "a bit springy" and is the trade the spec's stiffness scaling already makes.

  | Material | E, GPa (scaled) | Density, kg/m³ | Yield, MPa | Yield strain | Break strain |
  | --- | --- | --- | --- | --- | --- |
  | Steel | 200 (20) | 7850 | 350 | 0.0175 | 0.10 (ductile, about 6 × yield) |
  | Aluminium | 70 (7) | 2700 | 200 | 0.0286 | 0.08 (about 3 × yield) |
  | Carbon fibre | 120 (12) | 1600 | none (brittle) | 0.06 (never reached) | 0.05 (600 MPa strength) |

  **[assumption]** The break strains are game values, not real elongation at fracture (real ductile steel stretches 20% or more, which would look like toffee in a lattice).
- **[decision]** **Damping from a damping ratio.** Each beam gets `c = ζ · 2 · sqrt(k · m_a·m_b / (m_a + m_b))` with `k = EA / L`: `ζ = 0.05` for structure (the spec's minimum damping on every beam, enough to stop ringing without looking soft), `ζ = 0.6` for the sprung bay of a leg (no bounce).
- **[decision]** **Substep budget: at most 24 substeps for every default part and for the hopper** (cap 32, `c = 1`). The rule's `ω = sqrt(k · (w_a + w_b))` must stay under `24 × 60 = 1440`, so `EA ≤ 1440² · L · m / 2` for two equal nodes of mass `m`: about `3.2e7 N` for a tank member (L 0.625 m, 50 kg), `2.3e7 N` for an engine member (0.5 m, 44 kg), `6.5e6 N` for a leg member (0.5 m, 12.5 kg). At the scaled moduli those are areas up to about 46, 11 and 9 cm², and a real 4 mm aluminium tank wall of 1 m radius is about 31 cm² per longeron, so near-real parts fit.
- **[decision]** **Node-mass ratio at most 10 across a craft,** checked by the assembler (spec: mass limits in generators). The hopper's lightest nodes are leg nodes of about 12.5 kg, its heaviest merged ring nodes about 100 kg.

### The hopper (reference craft)

- **[decision]** Parts and numbers **[assumption]**, all tunable in 4.8 within the bands below:

  | Part | Mass | Shape | Material |
  | --- | --- | --- | --- |
  | Pod | 1200 kg | bottom ring 8 nodes at r 1.0 m, top ring 8 at r 0.6 m, height 1.2 m, apex node (17 nodes) | aluminium, never-live |
  | Tank | 2000 kg (partly filled) | r 1.0 m, length 2.5 m, 5 rings of 8 (40 nodes, 4 bays) | aluminium |
  | Engine | 800 kg, 80 kN | top ring 8 at r 1.0 m, nozzle ring 8 at r 0.5 m, height 1.0 m, head and tail on the axis (18 nodes) | steel, never-live |
  | Legs, four | 150 kg each | on alternate sides of the tank's lowest bay; about 2.4 m long, foot 1.2 m out from the tank wall and 0.5 m below the nozzle, foot square 0.35 m, foot radius 0.15 m | aluminium |

  Total 4600 kg, weight 45.1 kN, thrust to weight 1.77, hover throttle 0.564. About 110 nodes and 550 beams after welding.
- **[decision]** **Leg in three stages,** from the foot up: a sprung bay, a crush bay, the upper leg. Per leg **[assumption]**: the sprung bay reaches the crush force after 0.25 m (about `1.8e5 N/m`, so the 11.3 kN static share compresses it about 6 cm), `ζ = 0.6`; the crush bay yields at **45 kN** (4 × the static share) over a **0.3 m** stroke and breaks at its end (its members get their own yield and break strains, a "crush cartridge", not aluminium's); the upper leg's members yield at no less than twice the crush force in axial load. Why a crush bay: a stiff leg meets the ground with a peak force of `v · sqrt(k · m)`, hundreds of kN even at 1 m/s, so without one either every landing yields the leg or nothing ever does; a constant-force crush gives a clear, tunable energy budget, uses only what the core already has (yield as a force cap, break on total strain in compression), and real landers use crushable cartridges. The sprung bay in series stops small landings from crushing at all, and once the crush force is reached it holds there, so it never over-compresses.
- **[decision]** **Why those numbers give the bands** (level touchdown, all four feet at once). The sprung bays store `4 × ½ × 45 kN × 0.25 m = 22.5 kJ` before anything crushes, but gravity does `45.1 kN × 0.25 m = 11.3 kJ` of work over that travel, so they absorb about 11.2 kJ of landing energy: the hopper's kinetic energy at about 2.2 m/s, hence no yield at 2 m/s. At 3 m/s (20.7 kJ) the remaining 9.5 kJ goes into the crush bays at a net `4 × (45 − 11.3) kN ≈ 135 kN`, about 7 cm of their 0.3 m stroke. The crush bays run out at about 51.6 kJ in total, a touchdown of about 4.7 m/s; at 7 m/s (113 kJ) at least one runs out of stroke and breaks, and on rough ground one leg lands first and takes most of it. A first sketch at 34 kN and 0.15 m left gravity's work out and would have crushed at 1.2 m/s; corrected here before any code. **[assumption]** The uneven split on rough ground and the damping's share are what 4.8 measures and tunes.
- **[decision]** **Acceptance bands for 4.8** (the test of fun): stands 20 s on the pad with no yield; touchdown at 2 m/s on the pad, no yield; at 3 m/s on the pad and on five fixed rough spots, no break and the craft stands (tilt under 15°); at 7 m/s on the same five rough spots, in at least four of them a leg snaps (its foot no longer joined to the pod through live beams) and the craft tips over (engine-tail-to-pod-apex axis more than 60° from vertical, at rest). Four of five, not one: the fun must not depend on one lucky spot. What a 7 m/s touchdown on the flat pad does is recorded, not required.
- **[decision]** **Lift-off check:** pod height gain after 3 s at full throttle within 5% of `½ (T/M − g) t² = ½ × 7.58 × 9 ≈ 34 m`, tilt under 5°, no yield. Quantitative on purpose: it proves the thrust is the stated thrust, not just "it goes up".
- **[decision]** **Drops for tests, a hop for the story.** Tests place the craft at rest above the ground so that it touches down at a chosen speed (free fall carries no internal load, so the start is clean and exact). The hop (throttle up, drift, cut, fall) is one scripted scenario for the demo and the golden. The hopper has no steering, so the drift comes from a small sideways "nudge" thruster across the tank at about the centre of mass height (3 kN **[assumption]**), which costs two commands in a recording instead of a force per node per step.
- **[decision]** **Landing field: 65 × 65 points at 0.5 m** (32 m square): a flat pad and beside it bumps 0.3 to 0.8 m high and 1 to 2 m across (2 to 4 cells per bump, so the triangles show their shape), made with milestone 3's `bump` and `smoothstep`. Size from the golden budget: 4225 heights are about 705 records, 45 KB; the hopper about 42 KB more; a hop recording stays under 150 KB. Friction 0.8 as before.
- **[assumption]** **No floating origin.** A hop goes up a few tens of metres and drifts a few metres; milestone 3's reasoning (32-bit render positions finer than 0.1 mm within a few hundred metres) holds.
- **[assumption]** **Contact cost.** ER 003 measured about 0.1 ms per step with contact solves up to half of beam solves for a structure lying on the ground. The hopper has about four times the beams of the tower; a tipped-over hopper is the worst case. 4.7 and 4.11 re-measure with `scene_stats`; no optimisation is planned.

## 2026-11-17 (phase 4.1: materials and the part data model)

- **[action]** Built `src/parts/material.ts` (steel, aluminium and carbon fibre from the table above, scale `s = 0.1`, a member's `EA`, strains, yield force and mass per metre, reduced mass, damping from a ratio) and `src/parts/part.ts` (the part shape, `compilePart`, `partMass`, `partBudget`). Tests in `test/parts.test.ts` (13); `cargo test`, `pnpm test` (88, one skipped as before) and `pnpm typecheck` pass. The roadmap's milestone 4 heading now links the plan and the TL;DR no longer says the milestone needs its plan.
- **[decision]** **One beam resolver feeds both the commands and the budget.** `resolveBeam` gives a beam's rest length, compliance, damping and strains; `compilePart` sends them to the core and `partBudget` adds up `ω² = (1/m_a + 1/m_b) / compliance` from the same numbers with the same operations as `core/src/solver.rs`, so the reported substep count is the core's. Checked on eight lattices (a unit cube at four areas, mixed materials, one stiff strut among soft ones, a soft override, a single strut): every count equals what `World.step()` returned, and the set reaches the minimum (4), the cap (32) and values between. The part is treated as one island, which a connected part is; a craft of several islands takes the largest.
- **[decision]** **A beam can override the material's stiffness and strains** (`override: { ea, yieldStrain, breakStrain }`), which the leg's sprung bay (soft) and crush bay (own yield and break) in 4.3 need. Damping still comes from the ratio and the overridden stiffness.
- **[decision]** **Brittle carbon fibre** gets a yield strain of 1.2 × its break strain (`BRITTLE_YIELD_FACTOR`), so it can never yield first, and no yield force (`null`). Its break strain 0.05 times its scaled modulus is 600 MPa × area, a real strength.
- **[decision]** **Part mass and nodes:** every node of a part has positive mass (no pinned nodes in parts); a part's mass is the node masses added in index order, so the same part always gives the same total. Generators fill each node's mass (members' share plus contents, as decided above); 4.1 only checks it is positive.
- **[decision]** **`compilePart` does not emit thrusters yet.** The core learns them in 4.6; the thruster list is in the part shape and is carried through. A part compiled into an empty world has node `i` of the part at world node `i`.
- **[decision]** **Budget constants live in `part.ts`** (`SUBSTEP_BUDGET` 24, `NODE_MASS_RATIO_BUDGET` 10, and the core's rule constants mirrored as `SUBSTEP_MIN`, `SUBSTEP_MAX`, `SUBSTEP_C`); the lattice test would fail if the mirrored rule ever drifted from the core.
- **[finding]** **A strut yields at `σ_y · A` and breaks at its stated strain**, in the core, for steel and aluminium, in tension and in compression (two free 1000 kg nodes, gravity cancelled, a force ramped over 3000 steps to 1.02 × yield, then held 0.1% over it so the strut flows to its break). First yield event at 139,991.6 N for steel (σ_y · A = 140,000 N, −0.006%) and 79,995.2 N for aluminium (80,000 N, −0.006%); strain at that step 0.017501 and 0.028573 against 0.0175 and 0.028571. Break reported at total strain 0.100347 (step before: 0.099958) and 0.080082 (0.079714) against 0.10 and 0.08: at the stated strain plus at most one step of flow (0.35% and 0.10%). Tension and compression agree to 1e-9. The test asserts 1% on the force, 2% on the yield strain and under 0.005 of strain overshoot.
- **[finding]** **The damper alone limits plastic flow.** A first hold of 0.01% over yield did not reach the break in 1500 steps: the beam's damper (`c = 0.05 · 2 · sqrt(k · μ)`, 6.3 kN·s/m for the test strut) holds the flow to `excess / c`, about 2 mm/s. A hold of 0.1% over reaches the break in about 4 s. Worth knowing for the landing in 4.8: a crush bay yielding at its force moves at a speed set by the load above the cap divided by its damping, so a crush bay's damping ratio is a tuning knob for its stroke, not just for ringing.
- **[finding]** **The core adds its own decay of about `ω² · h / 2` on top of the damping ratio**, from its implicit stepping (substep `h = 1/60 / n`). A zero-damping spring at `ω = 20 rad/s` and 4 substeps decays at 0.83 /s, so `ζ = 0.1` gave 2.81 /s against the formula's 2.0. At the top of a structure's spectrum (`ω · h` near 1, the substep rule's limit) this is a large extra damping: the fastest modes of a stiff lattice die almost at once whatever `ζ` says, and the slow modes (the ones that look like wobble) get the formula's damping. That is the right way round for looks, and it means `ζ` is the damping of the slow modes only. The test uses `ω = 3 rad/s`, `ζ = 0.3` (masses 300 and 100 kg, so the reduced mass is exercised): decay measured by fitting peak heights, parabola-interpolated, at 0.915 /s against 0.900 /s (1.7%, under the 5% asked).
- **[oracle-candidate]** Is `ω² · h / 2` of numerical damping from the small-steps solver acceptable for the slow, visible modes of a tall rocket (milestone 5's wobble check), or should the solver's damping be corrected for it so that `ζ` means what it says at every frequency?

## 2026-11-18 (phase 4.2: truss and tank generators)

- **[action]** Built `src/parts/shared.ts` (exact ring points, mass distribution, the tube builder both generators share), `src/parts/tank.ts` and `src/parts/truss.ts`. Tests added to `test/parts.test.ts` over a sweep of six tanks (every ring count) and five trusses; `cargo test`, `pnpm test` (124, one skipped as before) and `pnpm typecheck` pass. The roadmap check "tank, truss, landing leg, engine and pod are generated from parameters" waits for 4.3.
- **[decision]** **Exact ring points.** Ring node counts are 4, 6, 8, 12, 16, 24 only. Points come from a table in 7.5° units built from exact values and half-angle square roots; a quarter turn is a swap and a sign, so opposite nodes are exact negatives and each node is within 1e-12 m of the stated radius. No sin or cos anywhere; `+ 0` removes a negative zero.
- **[decision]** **Tube layout.** Rings 0 and 1 are in segment 0 and ring `k` is in segment `k − 1`, so a seam sits between bays (`k = 1 … rings − 2`) and carries the axial area `ΣA` and the bending section `ΣA·d²` about the cut centroid. Every wall quad has its longitudinal member and both diagonals, and one skin panel of four non-flat tetrahedra (the fourth point is the node `max(2, n/2)` places round the same ring). End rings `bottom` and `top` are declared as attachment rings; side mount patches are one per quad.
- **[decision]** **In-ring bracing:** the perimeter, chords skipping one node, for 12 nodes and up the quarter chords (skip `n/4`), and the diameters; all flagged `ring: true`. The square truss has its two diagonals, the triangle just its three sides.
- **[finding]** **Perimeter plus skip-one chords is not enough from 16 nodes up.** The triangles they make are near flat (150° and more), so the ring has almost no stiffness against the squash that makes them flatter; a tube standing on the ground, or squeezed along its axis, went unstable whatever the damping or friction. Adding the quarter chords (right triangles with the diameters) settles 16 and 24 nodes and a 12-node tank, and costs `n` more beams per ring.
- **[decision]** **Mass.** Each member's own mass (density × area × length) goes half to each end node; the rest of the stated mass is spread evenly over all nodes, with the rounding left on the last node so the sum in index order equals the stated mass exactly. A stated mass under the members' own is refused with the numbers. A truss may leave the mass out and then weighs only its members.
- **[decision]** **Sweep masses are chosen to stay in the budget.** A light, stiff part has few kilograms per newton of stiffness and goes over 24 substeps (the per-beam rule); the sweep tank in carbon fibre is stated at 2000 kg for that reason.
- **[finding]** **A slender truss standing on three or four end nodes rocks, with growing swings over seconds.** Lateral rigid rocking on the ground contacts, not a mechanism in the lattice (the same truss lying on a face rests to under 1 mm/s). Not diagnosed. The rest test stands tanks and short trusses upright and lays slender trusses on their side; this is to be revisited when 4.7 stands a whole craft on legs.
- **[finding]** **The substep rule looks at each beam alone,** so a node with many beams on it (a ring node has up to 14) is stiffer than the budget number says. Parts that pass the budget still rest and squeeze correctly in the tests, so nothing was changed; a note for 4.7.
- **[finding]** **Squeezing a floating body with two fixed-direction forces turns it.** The test of "squeezed across a diameter springs back" first used forces along x, which act like a compressed rod and slowly rotate a free body; the gap then drifted by more than the squeeze. The test now re-aims both forces along the line between the two nodes each step, and ramps them in and out smoothly. Deflection is under 2% of the radius and the residual under 5% of the deflection for 6, 8, 12 and 24 nodes; with the ring members removed the same push squeezes more than five times as far, so the test can see a mechanism.
- **[oracle-candidate]** Why does a slender lattice standing on its end nodes rock with growing swings (contact point push-out and friction on three or four small spheres, or the per-substep ordering of beams then ground), and is that a defect to fix in the core before legs arrive?

- **[action]** Built `src/parts/leg.ts`, `src/parts/engine.ts` and `src/parts/pod.ts`; the frustum builder both engine and pod use (`buildFrustum`) and `distributeMass` moved into `src/parts/shared.ts`, and `ringBracing` moved there too (still re-exported from `tank.ts`). Tests added to `test/parts.test.ts`: three engines, three pods and two legs through the same sweep as the tank and truss (compiles, exact mass, inside the budget, rests 10 s with no yield and under 1 mm/s, byte-identical twice), the leg press tests, the engine and pod thrust tests, panels, shape and refusals. `cargo test`, `pnpm test` (147, one skipped as before) and `pnpm typecheck` pass. The roadmap check "tank, truss, landing leg, engine and pod are generated from parameters" is ticked; milestone 4 is 25%, overall 35%. A wireframe of the five parts was rendered headless into the local `artifacts/parts/`.
- **[decision]** **Engine and pod** are the same bell-or-shell frustum from two rings. The engine has a tail node on the axis at the nozzle and a head node on the axis at the top, both braced to both rings, and one thruster tail to head (`+y`); its attachment ring is the top ring. The pod has an apex node above the top ring (default rise half the top radius, a flat nose is refused as a mechanism) braced to every top-ring node, a skin panel on every nose facet, and its attachment ring is the bottom ring. Both are never-live. Both use the tank's ring counts, exact ring points, wall bracing and mass rule.
- **[decision]** **Leg layout.** Five stations of four nodes: the mount patch, the top and bottom of the crush bay, the bottom of the sprung bay, the foot. Four bays of twelve beams (four longerons and eight diagonals): the upper leg (ordinary members), the crush bay, the sprung bay and a short foot adapter (15% of the length) that carries the leg from the wide body square to the foot's size. `bodyWidth` (default the widest of mount and foot) is the square the three middle stations share, so both soft bays are straight prisms. Bay lengths are 2.5 times the stroke they must allow; the upper leg gets the rest and must be at least a quarter of the length.
- **[decision]** **Crush bay numbers.** Every member of the crush bay yields at the same strain of the bay along its axis (2%) and breaks at the same stroke, so the bay as a whole yields at the crush force `F_c`: each member's own yield force is its share of `F_c` over its cosine to the axis, and its `ea` is that yield force over its yield strain. The four longerons carry 75% of `F_c` and the eight diagonals the rest (`CRUSH_LONGERON_SHARE`).
- **[decision]** **Sprung bay numbers.** Every member has one spring constant along its own length, chosen so that the bay is a spring of `sprungStiffness` along the axis (`κ = K_s / Σcos²`); it yields at 1.5 strokes and breaks at 3, damped to ζ = 0.6. A spring that would yield below 1.1 times the crush force is refused with the numbers. An upper leg whose four longerons carry under twice the crush force is refused, with the member area it would need.
- **[decision]** **Hopper-like default sizes** used in the tests: pod 1200 kg aluminium, 8 nodes, radius 1.0 to 0.6, height 1.2; engine 800 kg steel, top radius 1.0, nozzle 0.5, height 1.0, 80 kN; leg 150 kg each, 2.4 m long, 1.2 m outward, crush 45 kN over 0.3 m, spring 500 kN/m over 0.12 m. Member areas: 4e-4 m² for engine and pod, 2e-4 m² for the leg. These are first numbers; 4.7 and 4.8 tune them.
- **[decision]** **The leg press test uses a guided platen.** The mount is pinned and a force along the leg's axis is ramped on the foot nodes; four stiff guides on the foot keep it square to the axis and give no push along it, as the platen of a press would. The thrust tests pin the engine's top ring (the tank above holds it) and cancel weight.
- **[finding]** **A soft sprung bay of four axial springs folds under a few kN of axial load.** Four springs have almost no bending stiffness, so a leg pushed along its axis buckled sideways long before the crush force. Fixed by making the soft bays wide squares (the 0.7 m body) with stiff oblique wedges at both ends; the guided platen removes the rest of the sideways error in the test. A real landing is not guided, so 4.8 will show whether the leg survives a landing at an angle.
- **[finding]** **Soft rings let the bay's squares spread under the diagonals' push,** and the longerons then carried about 20% more than their design share: with the share at 0.2 the first yield was at 0.82 of the crush force, at 0.5 at 0.90, at 0.75 at 0.955 (first yield at 0.954 in the test, collapse at about 0.98). The test accepts a first yield between 0.9 and 1.05 of the crush force.
- **[finding]** **A perfectly plastic crush bay breaks early.** The bay shortens at a nearly constant force once it yields, but its members have no restoring force against unequal strain, so one runs ahead and the first break comes at about 40 to 50% of the designed stroke, not at 100%. The test asserts at least 25% of the stroke before the first break. A designed 0.3 m stroke is therefore worth about 0.12 to 0.15 m of absorbed travel; 4.8 tunes with that. Giving the members a little hardening after yield would make the break come later and more evenly; not done, since the engine has no hardening.
- **[finding]** **Nothing outside the crush bay yields or breaks before the bay breaks** (upper leg, spring, foot adapter, every ring), in both legs tested. Below 0.9 of the crush force nothing yields at all and the bay shortens elastically by under 8% of its stroke.
- **[finding]** **Free-body thrust tests tumble.** The engine pushed up on its tail and head with balancing forces on its top ring, with nothing pinned, rotated in seconds with no yield (a fixed-direction load on a floating body; the same as the squeeze test in 4.2). With the top ring pinned the largest strain is 5% of yield at 80 kN. The pod's test lets it accelerate freely under the full thrust (about 67 m/s² at 1200 kg), and nothing yields.
- **[finding]** **Budgets.** The leg is 19 substeps with a node-mass ratio of 1.24; the steel engine is 17; the aluminium pod is 7. The craft's ratio will be much higher: a leg's nodes weigh about 7.5 kg against about 100 kg for merged ring nodes at a joint. 4.4 and 4.7 recompute and log it.
- **[oracle-candidate]** Should a crush member get a small hardening after yield, so a crush bay absorbs its whole designed stroke before the first break, or is the early break (40 to 50%) the behaviour we want for the hard-landing snap?

## 2026-11-18 (phase 4.4: attachment rings and the assembler)

- **[action]** Built `src/parts/assemble.ts` (`assemble(assembly)` gives one craft that is a part, so `compilePart`, `partBudget` and `partMass` work on it) and `test/assemble.test.ts` (13 tests). `cargo test`, `pnpm test` (160, one skipped as before) and `pnpm typecheck` pass. No roadmap check is ticked by this phase ("join at rings, saved and loaded" waits for 4.5), so the percentages stay at 25% and 35%.
- **[decision]** **The weld.** A child's ring is placed against the parent's (axes opposed, centres equal), turned a whole number of ring steps, and merged into the parent's nodes; the merged node keeps the parent's segment and the masses add. Which child node meets which parent node comes from the ring sense, worked out from the geometry (two rings running the same way round, seen along the shared axis, pair `j` with `j + clock`; opposed ones pair `j` with `clock − j`), so a clock is a permutation and never an angle. Every merged pair must land within 1 mm, else the join is refused with the two node numbers and the distance. The root may be placed by a shift and a turn in whole 15° steps, nothing else.
- **[decision]** **Seams.** Each join makes one seam between the parent's segment and the child's first segment: area `ΣA·cos²θ` and bending `ΣA·cos²θ·d²` over the seam beams, taken about the cut centroid. A beam of a child that touches a merged node is a seam beam and is marked. The child's own ring beams are dropped (the parent's stay).
- **[decision]** **Legs weld on a mount patch.** The patch's four nodes pair a to a, b to b, c to c and d to d, the clock must be 0, and the parent's patch must face outward from the parent's node centroid (a leg cannot be joined to the inside of a tank). A patch that shares a node with a patch already used is refused, which is how two legs on neighbouring quads are caught.
- **[decision]** **Refusals,** each with its reason in the message and nothing changed (the parts given are never touched): no root, duplicate part, unknown part, unknown ring or patch, bad clock (not a whole number), a part joined to itself, attached twice, a cycle, a part no join reaches, ring or patch already used, a ring joined to a patch, node counts differ, radii differ by over 1 mm, rings or patches that do not land on each other, a patch facing inward, a clock on a patch, and the two craft budgets below.
- **[decision]** **A craft's node-mass ratio budget is 20, not 10.** A single part keeps 10. The hopper measures **18.16** (heaviest node 120.2 kg, lightest 6.62 kg): the heavy nodes are the tank's bottom-ring nodes, which take the engine's ring and a leg's mount node as well as the tank's own share. The hopper stands on flat ground for 20 s with no yield, break or freeze, at rest under 1 mm/s, using 19 substeps (budget 24), so 20 is the limit the assembler refuses over (`CRAFT_NODE_MASS_RATIO_BUDGET`); the substep budget stays 24. Raising it is cheap to revisit if 4.7 shows trouble when the engine pushes.
- **[finding]** **Hopper numbers.** Seven parts (pod, tank, engine, four legs) are 155 nodes; 32 merge (8 + 8 + 4 × 4), so 123 nodes and 612 beams, mass exactly 4600 kg. The tank's own seams plus six joins (pod, engine, four legs). The legs' mount is the tank's `side-0-0/2/4/6` quad (0.765 m by 0.625 m), so the leg's `mountWidth` and `mountHeight` come from the tank's patch nodes; a mount of another size is refused.
- **[finding]** **The leg's foot hangs 0.77 m below the nozzle,** not the 0.5 m the planning section guessed. Plenty of clearance for the engine; the height of the legs is a tuning number for 4.7 and 4.8.
- **[finding]** **Terrain is not counted as nodes in the world,** so a test that stands a craft on `flatTerrain` sees exactly the craft's nodes and beams in `nodeCount` and `beamCount`.
- **[oracle-candidate]** Is a flat 20 for the craft's node-mass ratio the right rule, or should the budget be about the ratio between neighbours joined by a beam (which is what the solver feels) rather than across the whole craft?

- **[decision]** **Canonical text.** JSON, two-space indent, one newline at the end, top-level keys in the order format, version, root, place, parts, joins; each part is id, type, params, each join child, childPort, parent, parentPort, clock, and params follow a fixed order per part type. Parts and joins keep their order, since that is the order of the craft's nodes. Keys in a file to be read may come in any order; saving puts them right. ## 2026-11-18 (phase 4.6: thrusters in the core)

- **[action]** Added `core/src/thrust.rs` (the force pass), thruster arrays in `World`, the commands `CMD_ADD_THRUSTER` (9) and `CMD_SET_THROTTLE` (10) in `core/src/command.rs` and `src/commands.ts` (`addThruster`, `setThrottle`), thrusters in the state hash, `ABI_VERSION` 4, and a recording decoder that reads ABI 2, 3 and 4. New tests: `core/tests/thrust.rs` (9), a thrusting-scene golden in `core/tests/ffi.rs`, and two wasm tests in `test/wasm.test.ts`. `cargo test`, `pnpm test` (175, one skipped as before) and `pnpm typecheck` pass. No roadmap check is ticked ("engines produce thrust and the craft lifts off" is 4.7), so the percentages stay at 50% and 38%.
- **[decision]** **The push.** Each step, before the islands are built, each thruster with a throttle above zero adds `throttle × maximum` along the unit vector from tail to head, half on each node, through `add_force`, using the positions at the start of the step. Thrusters are visited in index order, so the sum is deterministic. A thruster whose nodes coincide, or whose direction is not finite, gives nothing.
- **[decision]** **Thrusters remember their nodes' generations.** The generation of each node is stored when the thruster is added, and the thruster is off whenever either node is dead or its slot has been reused. So a deleted node turns its thruster off for good, even when a new node later takes the same slot. The throttle can still be set on such a thruster (it exists), and it pushes nothing.
- **[decision]** **The hash adds a thruster section only if any thruster exists** (count, then per thruster tail, head, maximum bits, throttle bits; generations are not hashed, they follow from the nodes). Every earlier world hashes as before, so the small bench, hand-built, terrain and both committed recordings keep their hashes unchanged.
- **[decision]** **Rejected records:** `ADD_THRUSTER` is refused unless both nodes are live, they differ, and the maximum is finite and not negative (zero is allowed); `SET_THROTTLE` is refused unless the thruster exists and the throttle is from 0 to 1 (NaN fails). The rest of the batch applies.
- **[decision]** **Recording decoder reads ABI 2 to 4.** ABI 3 and 4 only added command kinds and one hash section that older worlds do not have, so every older list means the same thing. The two committed recordings stay as they were (ABI 2 and ABI 3); their tests now compare the fresh file with the stored one except for the ABI field, as the weak bridge already did.
- **[finding]** **The two-node pair measures right.** A 30 kg and a 70 kg node tied by a beam, with 3000 N at full throttle for one second, end with total momentum 3000 N·s along x within 1e-6 relative (speed 30 m/s), gravity untouched, and the beam gap within 1 mm of its rest length.
- **[oracle-candidate]** Should the push be split half and half between the two nodes, or weighted by inverse mass so the nozzle end takes more? Half and half keeps the force on the line between the nodes with no torque, but at large mass ratios it shakes the lighter node harder.
